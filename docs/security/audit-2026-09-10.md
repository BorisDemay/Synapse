# Security audit — 2026-09-10

Reviewed source: `e42593b`. Context: private, single-user development deployment.
This is a source review with bounded local reproductions, not a production
certification or an external penetration test. No application fixes or live
account changes were made.

The immediate priorities are keeping development services private, updating the
development toolchain, and bounding ZIP decompression. The reviewed encryption
and authorization paths have useful protections; this review did not demonstrate
a plaintext vault leak or a cross-account HTTP authorization bypass.

## 1. Development deployment is not restricted to loopback

**Priority: high if reachable by another person; conditional deployment risk.**

Sources: `docker-compose.yml:35`, `docker-compose.yml:80`,
`infra/caddy/Caddyfile:2`, `apps/server/src/auth/mod.rs:49`.

Compose publishes port 8080 without a host address, disables HTTPS in its bundled
Caddy configuration, defaults to insecure cookies and public signup, and starts
in development mode. The observed `synapse-caddy-1` container publishes
`0.0.0.0:8080` and `[::]:8080`. Read-only inspection of `synapse-server-1` confirmed
`SYNAPSE_ENV=development`, `SYNAPSE_COOKIE_SECURE=false`, and
`SYNAPSE_ALLOW_PUBLIC_SIGNUP=true`.

The source seeds an activated `test` / `test` account outside production. More
significantly, each development restart resets that account's password to
`test`, even after a password change. Anyone who can reach this API can use that
known account. They can obtain its ciphertext and key envelopes, attempt offline
passphrase guessing, and mutate/delete its data; login alone does not decrypt a
vault. Other users' private vaults remain subject to authorization checks.

External reachability was **not** established: host firewalls, NAT, private
network access controls, and any outer TLS proxy were not assessed. The running
container's source revision was not established either. Runtime authentication
probes used the freshly built source and a disposable database, not live accounts.

**Action:** for same-machine use, publish the proxy on `127.0.0.1` explicitly.
For remote personal access, restrict it to the intended private access path and
use HTTPS. Make fixture seeding explicitly opt-in and stop overwriting existing
credentials. Disabling public signup alone does not disable the fixture account.
Do not simply delete a fixture account that owns your only copy of a vault.

## 2. Production-only dependency auditing misses vulnerable development tools

**Priority: medium now; high/critical under the relevant exposure conditions.**

Sources: `apps/web/package.json:35`, `apps/desktop/package.json`, `package.json`,
`pnpm-lock.yaml`, `justfile` (`audit-js`).

Observed results:

| Command | Result |

| `pnpm audit --prod --json` | 0 reported vulnerabilities |
| `pnpm audit --json` | 17 advisories: 1 critical, 3 high, 11 moderate, 2 low |

The installed graph includes Vite 6.1.0, Vitest 3.0.5, and Playwright 1.50.1.
Examples relevant to development:

- Vite's WebSocket file-read advisory affects an exposed development server.
  The normal web script binds localhost, which reduces this exposure.
  [Maintainer advisory](https://github.com/vitejs/vite/security/advisories/GHSA-p9ff-h696-f583).
- The critical Vitest issue requires its UI/API server to be listening; it is
  not evidence that ordinary `vitest run` gives an attacker code execution.
  [Maintainer advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp).
- Playwright's reported issue concerns browser download certificate validation,
  rather than Synapse's runtime API. The audit identifies versions before 1.55.1.
  [Advisory](https://github.com/advisories/GHSA-7mvr-c777-76hp).

**Action:** audit the full graph in development/CI, update compatible toolchain
versions and regenerate the lockfile, then run build/tests and audit again.
The current audit reports Vite fixes through 6.4.3, Playwright >=1.55.1, and a
separate Vitest/mocker advisory requiring >=4.1.11; upgrading Vitest only to
3.2.6 would not clear every current finding. Compatibility remains to be tested.

Rust advisory checks passed with repository exceptions. Repeating the desktop
check with an empty ignore list reported six **unmaintained dependency** notices
(proc-macro-error and five rust-unic crates), not six demonstrated exploitable
vulnerabilities. Keep these exceptions explicit and reviewable.

## 3. ZIP limits are checked after complete synchronous decompression

**Priority: medium, including for a private/offline app.**

Source: `apps/web/src/import/markdown-folder.ts:156` (shared by desktop).

`planZipImport` calls `unzipSync(bytes)` before `planMarkdownImport` checks the
10,000-entry and 250 MiB limits. Every entry is expanded before it can be rejected,
on the calling JavaScript thread. An imported archive can exhaust memory or
freeze the editor before the import preview/confirmation appears.

**Reproduction:** a synthetic ZIP containing a single 251 MiB repeated-byte note
was 255,946 bytes compressed. Calling the actual TypeScript function under Node
returned `Import is too large` only after expansion; the observed ArrayBuffer
memory delta was 259,305,980 bytes. The probe deliberately stayed bounded and did
not attempt a crash. A browser crash and loss of an unsaved draft are possible
impacts, not outcomes demonstrated here.

**Action:** validate entry counts and declared sizes before inflation, then enforce
actual per-entry and cumulative output limits while streaming. Run decompression
in a cancellable worker. A compressed-file-size check alone is insufficient.

## 4. Direct API callers can bypass authentication throttling

**Priority: medium; strongest relevance when the API is directly reachable.**

Sources: `apps/server/src/lib.rs:30`, `apps/server/src/main.rs:63`.

The rate limiter trusts the first `X-Forwarded-For` value supplied by any caller,
without checking whether the peer is a trusted proxy. A caller can change that
value on each request to obtain a new bucket. The binary also does not install
`ConnectInfo`, so its intended peer-address fallback becomes `unknown-client`.
Direct callers without forwarding headers consequently share one bucket.

**Local HTTP evidence:** eight invalid logins with one header value returned
`401,401,401,401,401,429,429,429`. Eight requests with different header values
returned eight `401`s, with no throttling. These used a nonexistent synthetic
account and did not perform a password attack.

The bundled Caddy path mitigates header spoofing: Caddy ignores incoming
forwarding-header values by default. This is not a demonstrated bypass through
that proxy. [Caddy header behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#defaults).

**Action:** supply actual connection information, ignore forwarded addresses
unless the peer is explicitly trusted, and select the client address according
to that trusted proxy chain. Add account-level and bounded global authentication
limits as appropriate; keep password hashing off async executor threads.

## 5. Revoked WebSocket sessions retain activity access

**Priority: medium; metadata and resource exposure, not plaintext disclosure.**

Source: `apps/server/src/http/ws.rs:90` and `:115`.

Session and membership checks happen only at upgrade. The connection loop retains
the user/vault IDs but no session token or expiry, so logout/revocation does not
stop later notices. It also does not recheck membership.

**Local HTTP/WebSocket evidence:** authenticate, open a socket, log out, confirm
that the old cookie now receives HTTP 401, log in again, and push a synthetic
operation. The old socket still receives a wake signal containing a cursor.
A revoked client can continue observing vault activity and occupying connection
slots. It cannot use its revoked cookie to pull ciphertext over HTTP.

**Action:** associate sockets with their sessions, close them on revocation,
and recheck expiry/membership before issuing notifications. Test logout,
password-change revocation, expiry, and membership removal with a live socket.
[OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html#session-management).

## 6. Origin enforcement is incomplete

**Priority: low under the current browser defenses; confirmed control gap.**

Sources: `apps/server/src/http/vaults.rs:32`,
`apps/server/src/http/sync.rs:39`, `apps/server/src/http/ws.rs:82`.

Vault creation and sync push omit the Origin checks already present on envelope
updates and logout. The WebSocket handshake also omits its Origin allowlist.
The security middleware adds CORS response headers; it does not reject these
requests before handlers execute.

**Local evidence:** supplying a valid synthetic session cookie and
`Origin: https://untrusted.example` returned HTTP 201 for both vault creation and
push, and HTTP 101 for WebSocket upgrade.

These raw-client tests **do not demonstrate browser CSRF**: JSON requests normally
require an allowed CORS preflight, and `SameSite=Strict` restricts cross-site cookie
transmission. Same-site hostile origins are a particular concern for WebSockets,
which do not use the normal CORS preflight. The result is nonetheless inconsistent
with the project's stated requirement for explicit Origin checks.

**Action:** centralize Origin validation on cookie-authenticated mutations and
WebSocket upgrades, and add missing/wrong/correct Origin tests for each route.

## Validation and scope

- `cargo build -p synapse-server`: passed.
- `cargo test -p synapse-crypto`: 10 tests passed, including tampering, wrong AAD,
  wrong passphrase, nonce reuse, redacted Debug, and web/Rust interoperability.
- Selected existing server suites: 50 tests passed. To avoid touching normal
  development/test data, temporary copies of auth, account settings, authorization,
  CSRF, sync push/pull, headers, telemetry, paths, and WebSocket tests changed only
  their database name to `synapse_audit_20260910`, then ran serially.
- Web crypto, auth store and encrypted cache: 45 tests passed.
- Markdown renderer and editor configuration: 24 tests passed.
- Native commands, local folder and updater boundaries: 20 tests passed.
- Both Cargo advisory checks passed under the checked-in ignore policy; the
  additional no-ignore desktop audit failed on the six maintenance notices above.
- Bounded HTTP, WebSocket, and ZIP probes reproduced the findings described above.

The 149 passing tests are evidence for their covered cases, not proof that these
security gaps are absent. Disposable server/database resources and the temporary
test source were removed afterward. No live vaults, credentials, or user data
were used in probes. Existing untracked `.worktrees/` content was left alone.

Not completed: external reachability testing, a live Windows/WebView assessment,
a new browser XSS fuzzing campaign, container/OS package scanning, a complete
release/backup/CI review, or an independent cryptographic audit. No full
`just verify` or production deployment was performed.

Known design limitations remain relevant: desktop Markdown replicas stay in
plaintext after locking; trusted-device unlock trusts the browser profile;
optional AI receives explicitly supplied plaintext. A compromised web host can
also replace the JavaScript delivered to a browser; ciphertext storage alone
does not defend an unlocked web client against malicious client code delivery.

## Remediation status

The current source applies the controls described above: production-safe Compose
defaults with explicit development fixture opt-in, trusted-peer rate limiting,
bounded sync responses and concurrency, transactional password changes with
bounded Argon2 workers, origin-checked and revocable WebSockets, streamed ZIP
metadata limits in a cancellable worker, strict browser CSP headers, full
dependency updates, and a full-graph `pnpm audit` gate. The regression command
`node tests/security/local-penetration.mjs` now fails on any finding and
completed with **31 checks and zero findings** on 2026-09-10.
